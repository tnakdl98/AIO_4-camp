# 3차시. 상담 컨텍스트를 FastAPI·Redis로 옮겨 복원하기

## 1. 학습목표

[수업 전 안내](../TODAY_GUIDE.md)를 먼저 읽습니다.

- 화면이 이력을 보내지 않아도 서버에서 앞선 상담을 복원합니다.
- 요청 검증·이력 보관·재시도의 API 계약을 확인합니다.

### 앞 차시와 무엇이 달라지나요?

| 출발점 | 이번에 새로 완성할 기능 | 완료 산출물 |
| --- | --- | --- |
| 브라우저 연결이 대화 기록을 소유 | 서버가 Redis에 문의를 보관하고 ID로 복원 | 브라우저가 달라도 같은 문의 이어가기 |

기본 코드는 해당 기능이 정상 작동하는 완성 예제입니다. 실행 결과를 먼저 확인하고 업무 조건이나 표시 한 곳을 바꿉니다. 각 차시의 수정 과제는 다음 차시 실행의 전제 조건이 아닙니다.

## 2. 중요 알고리즘 및 코드를 읽을 때 반드시 알아야 할 내용

브라우저 연결이 끊겼다고 상담을 처음부터 시작할 수는 없습니다. 이제 대화 보관을 서버로 옮깁니다. 화면은 문의 ID와 새 질문만 보내고, FastAPI가 Redis에서 문의 카드와 성공 이력을 읽어 Groq input을 만듭니다.

| 요청 | 보내는 값 | 서버가 맡는 일 |
| --- | --- | --- |
| POST /tickets | 문의 카드 네 항목 | ID 발급과 빈 상담 보관 |
| GET /tickets/{id} | 문의 ID | 카드·성공 턴 복원 |
| POST /tickets/{id}/turns | question·request_id | 이력 조회, Groq 호출, 성공한 턴 저장 |

JSON 요청의 question은 FastAPI가 TurnInput으로 검사해 `body.question`에 넣습니다. ticket_id는 URL에서 받아 UUID로 검사합니다. UI가 과거 history를 다시 보내지 않으며 임의로 서버 이력을 덮어쓰는 필드도 없습니다.

질문과 답변은 성공한 뒤 한 턴으로 함께 저장합니다. request_id는 같은 전송을 다시 확인하는 번호입니다. 같은 번호·같은 질문은 기존 결과를 반환하고, 번호가 같은데 질문이 다르면 409입니다. 동시 변경은 Redis WATCH가 감지해 409로 중단하므로 조용히 기록을 덮어쓰지 않습니다.

Redis 문의는 마지막 성공 저장 후 30분 유지됩니다. 조회나 기존 결과 재확인만으로 수명이 늘지는 않습니다. 한 문의는 최대 12턴이며, 영구 저장소가 아닙니다. 이 차시는 로그인 없는 본인 PC 테스트이므로 서버를 127.0.0.1에 실행합니다. 계정별 권한은 4차시에서 추가합니다.

### 핵심 코드

```python
class TurnInput(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    request_id: UUID
    question: str = Field(min_length=1, max_length=1000)
```

전체 실행 코드는 [main.py](main.py)에 있습니다. 이번 수정 대상은 **backend03/main.py의 TurnInput**입니다. 준비된 인증·통신 코드를 모두 다시 작성하지 않고 현재 기능이 해결하는 문제를 확인합니다.

참고: [FastAPI 요청 본문](https://fastapi.tiangolo.com/tutorial/body/), [Redis 파이프라인·WATCH](https://redis.io/docs/latest/develop/clients/redis-py/transpipe/).

## 3. 코드 제공

### 준비와 실행

[서버 준비](../BACKEND_GUIDE.md)의 backend03을 먼저 실행합니다. 화면의 .env에는 API_BASE_URL=http://127.0.0.1:8000만 두며 Groq 키는 백엔드에 둡니다.

Windows CMD에서 현재 차시 폴더로 이동합니다. 경로는 실제 압축 해제 위치에 맞춥니다. 정상 수업 가상환경을 사용하며, 처음 환경 준비는 [서버·환경 안내](../BACKEND_GUIDE.md)를 따릅니다. **기존 .env가 있으면 copy 명령을 생략**합니다.

```bat
cd /d C:\AI4\Groq_MultiTurn_Morning\lesson03
python -m pip install -r requirements.txt
copy .env.example .env
python -m streamlit run main.py --server.address 127.0.0.1 --server.port 8501
```

브라우저에서 http://127.0.0.1:8501 을 엽니다. main.py 파일 미리보기가 아니라 이 주소가 실행 화면입니다. 화면 서버 종료는 해당 CMD의 Ctrl+C입니다.

### 실습 순서

1. 서버와 화면을 실행합니다. `회의실 마이크 문의`, 서비스 화상회의, 환경 `Windows 11 / Chrome`, 영향 본인만으로 **서버에 문의 만들기**를 누릅니다. 표시된 문의 ID 전체를 메모합니다.
2. `녹음 앱에서는 마이크가 되는데 회의 웹페이지에서만 소리가 안 납니다.`를 전송하고, `브라우저 마이크 권한은 허용으로 확인했습니다.`를 이어 전송합니다.
3. 브라우저의 **새 시크릿 창**에서 같은 앱 주소를 엽니다. 다시 열 문의 ID에 메모한 전체 ID를 넣고 **기존 문의 열기**를 누릅니다. 이전 두 턴이 복원되는지 확인합니다.
4. `그다음 확인할 것을 하나만 알려주세요.`를 보냅니다. 화면은 이력을 전송하지 않았지만 서버가 과거 네 메시지를 input에 넣었는지 표시 숫자로 확인합니다.
5. **backend03/main.py의 TurnInput 한 곳**에서 question의 `max_length=1000`을 `max_length=300`으로 바꿉니다. 백엔드 CMD에서 Ctrl+C를 누르고 같은 명령으로 다시 시작합니다. Redis는 계속 켜 둡니다.
6. http://127.0.0.1:8000/docs 에서 POST /tickets/{ticket_id}/turns를 펼치고 Try it out을 누릅니다. ticket_id에 내 ID를 넣고 아래 모양으로 보냅니다. question에는 실제로 `가` 301개를 넣습니다. 생성은 별도 CMD에서 `python -c "print('가' * 301)"`로 할 수 있습니다.

```json
{"request_id":"33333333-3333-4333-8333-333333333333","question":"여기를 가 301개로 바꿉니다"}
```

7. 422가 반환되고 턴 수가 증가하지 않아야 합니다. 수정 전에는 같은 301자가 입력 검사를 통과합니다. 수정 후 짧은 질문은 계속 처리됩니다. 실패 버튼의 복구는 아래 접이식 순서를 따릅니다.

### 예상 결과

| 조작 | HTTP/화면의 예상 결과 | 기록 변화 |
| --- | --- | --- |
| 문의 생성 | 201, id=<새 UUID>, turn_count=0 | 카드만 생성 |
| 첫 질문 성공 | 200, context_message_count=0, input_count=2 | 1턴 |
| 두 번째 질문 성공 | 200, context_message_count=2, input_count=4 | 2턴 |
| 시크릿 창에서 ID로 재조회 | 200, 카드와 두 턴 복원 | 변화 없음 |
| 복원 후 세 번째 질문 | context_message_count=4, input_count=6 | 3턴 |
| 입력 한도 300으로 수정 후 301자 요청 | 422, 화면 요청이면 입력창 재개 | 변화 없음, Groq 호출 없음 |
| 12턴 다음의 새 요청 | 409, 이유 안내 후 다른 문의로 이동 가능 | 12턴 유지 |
| 없는 UUID 문의 조회 | 404 | 변화 없음 |

**세 번째 AI 답변 예시**

```text
[증상 요약] 녹음 앱은 정상이고 회의 웹페이지에서만 문제가 있으며 브라우저 권한은 확인했습니다.
[확인할 정보] 회의 웹페이지에서 선택한 입력 장치가 실제 마이크와 일치하나요?
[다음 조치] 웹페이지의 입력 장치 선택을 확인해 주세요.
```

제목·환경·이미 시도한 조치를 반영해야 합니다. 같은 question과 request_id를 다시 보내면 200과 replayed=true이며 새 턴을 만들지 않습니다. question만 다르게 바꾸고 같은 번호를 보내면 409입니다. UUID와 응답 ID는 예시와 일치할 필요가 없습니다.

1. 문의를 열고 현재 성공 턴 수를 확인합니다. 서버는 켜 둡니다.
2. 연결 실패 실습을 펼쳐 다음 상담 한 번 실패시키기를 누릅니다.
3. 새 질문을 전송합니다. 실패는 서버에 보내기 전에 한 번 발생합니다.
4. 자동으로 다시 그린 화면에 오류·확인 중인 질문·요청 번호가 보이고 입력창이 잠깁니다. 성공 턴 수는 그대로입니다.
5. 같은 질문 다시 보내기를 누릅니다. 실패 예약은 이미 소모됐으므로 다시 실패 버튼을 누르지 않습니다.
6. 성공 후 턴 수가 하나만 늘고 입력창이 열립니다. 같은 번호 재확인은 새 턴을 만들지 않습니다.
7. 422 입력 거절이나 409 턴 한도 초과는 같은 내용 재시도로 해결되지 않습니다. 이때는 pending을 해제하고 거절 이유·수정이 필요한 질문을 표시합니다. 입력을 고치거나 다른 문의로 이동해 새 문의를 만듭니다.

이 장치는 저장 후 응답 유실을 재현하는 것이 아닙니다. 서버 자체 Groq 호출 오류도 성공한 턴을 저장하지 않지만, 실제 한도를 일부러 소진할 필요는 없습니다.

### 복습 과제

Swagger에서 같은 요청 번호·같은 질문을 두 번 보낸 뒤 replayed와 턴 수를 비교하세요. 다음에는 같은 번호에 다른 질문을 넣어 409와 기록 불변을 확인하세요. 비밀키는 요청 본문에 넣지 않습니다.

입력과 예상 결과 중 실제로 확인한 항목을 짧게 남깁니다. 실제 직원의 정보 대신 수업용 가짜 문의를 사용합니다.
