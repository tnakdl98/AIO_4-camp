## 2. 중요 알고리즘 및 코드를 읽을 때 반드시 알아야 할 내용

문의 ID가 있다고 해서 다른 직원의 상담을 열 수 있어서는 안 됩니다. 문의 ID는 찾아갈 주소이고, 로그인한 사용자가 그 문의의 주인인지 확인하는 것은 별도의 권한 검사입니다.

UI는 `Authorization: Bearer 토큰` 헤더를 보냅니다. `Depends(bearer)`가 이 헤더를 읽어 require_user의 credentials에 전달합니다. 가짜 헤더 `Bearer demo-token`이면 scheme은 Bearer, credentials.credentials는 demo-token입니다. `Annotated`에는 매개변수 타입과 FastAPI가 값을 넣는 방법이 함께 적혀 있습니다.

HTTPBearer는 토큰을 꺼낼 뿐 유효성을 확인하지 않습니다. require_user는 Supabase get_user(token)과 기존 Redis 로그인 등록을 확인한 뒤 사용자 ID를 반환합니다. FastAPI가 `Depends(require_user)`의 반환값을 경로 함수의 user에 넣습니다.

문의 생성 때 owner_id는 이 검증 결과로 정합니다. 읽기와 상담 요청마다 checked_ticket이 저장된 owner_id와 비교합니다. 요청 본문에 owner_id를 보내 소유자를 바꿀 수 없으며, 모르는 ID와 다른 계정의 ID는 모두 404로 응답합니다.

로그아웃은 화면의 토큰·선택·미확정 질문을 지우고 해당 토큰의 Redis 앱 등록을 삭제합니다. 문의 본문은 30분 수명 동안 남으므로 같은 계정으로 다시 로그인하면 내 목록에서 다시 열 수 있습니다. 타인 문의에 접근할 수 없는지 확인하려고 이 검사를 끄거나 개인정보를 출력하지 않습니다.

### 핵심 코드

```python
def checked_ticket(raw, owner_id):
    if raw is None:
        raise HTTPException(404, "이 계정에서 찾을 수 없는 문의입니다.")
    ticket = json.loads(raw)
    if ticket["owner_id"] != owner_id:
        raise HTTPException(404, "이 계정에서 찾을 수 없는 문의입니다.")
    return ticket
```

전체 실행 코드는 [main.py](main.py)에 있습니다. 이번 수정 대상은 **lesson04/main.py의 ticket_label()**입니다. 준비된 인증·통신 코드를 모두 다시 작성하지 않고 현재 기능이 해결하는 문제를 확인합니다.

참고: [FastAPI HTTPBearer](https://fastapi.tiangolo.com/reference/security/), [Supabase get_user](https://supabase.com/docs/reference/python/auth-getuser).

## 3. 코드 제공

### 준비와 실행

[서버 준비](../BACKEND_GUIDE.md)의 backend04을 먼저 실행합니다. 화면의 .env에는 API_BASE_URL=http://127.0.0.1:8000만 두며 Groq 키는 백엔드에 둡니다.

Windows CMD에서 현재 차시 폴더로 이동합니다. 경로는 실제 압축 해제 위치에 맞춥니다. 정상 수업 가상환경을 사용하며, 처음 환경 준비는 [서버·환경 안내](../BACKEND_GUIDE.md)를 따릅니다. **기존 .env가 있으면 copy 명령을 생략**합니다.

```bat
cd /d C:\AI4\Groq_MultiTurn_Morning\lesson04
python -m pip install -r requirements.txt
copy .env.example .env
python -m streamlit run main.py --server.address 127.0.0.1 --server.port 8501
```

브라우저에서 http://127.0.0.1:8501 을 엽니다. main.py 파일 미리보기가 아니라 이 주소가 실행 화면입니다. 화면 서버 종료는 해당 CMD의 Ctrl+C입니다.

### 실습 순서

1. A 계정으로 로그인하고 `A-VPN-접속` 문의를 만듭니다. `A-확인-321 장치에서 VPN 시간 초과가 납니다.`를 전송합니다. 문의 ID 전체를 메모합니다.
2. **계정 바꾸기 / 로그아웃**으로 B 계정에 로그인합니다. B에게 새 문의가 없다면 **내 문의 목록: 0건**이 보입니다. B의 기존 문의가 있더라도 A의 제목·이력은 목록에 없어야 합니다.
3. B의 **다시 열 문의 ID**에 A의 ID를 붙이고 **기존 문의 열기**를 누릅니다. 화면에 404가 표시되어야 하며 A의 문장이 나타나면 안 됩니다.
4. B가 `B-회의실-마이크` 문의를 만들어 자신의 증상을 말합니다. 로그아웃한 뒤 A로 다시 로그인합니다. 내 목록에서 A의 문의 ID를 골라 복원하고 `앞에서 말한 장치와 오류를 요약해 주세요.`로 이어갑니다.
5. backend04의 http://127.0.0.1:8000/docs 에서 Authorize를 누르지 않은 상태로 GET /tickets를 실행하면 401입니다. 모델 API가 아니라 앱 인증 단계에서 거절된 것입니다.
6. 화면 파일 lesson04/main.py의 `ticket_label(room)` 한 곳을 아래처럼 바꿉니다. 현재 함수는 제목과 ID만 보여 줍니다. 수정 후 **다른 문의로 이동**을 눌러 내 목록의 턴 수가 함께 보이는지 확인합니다. owner_id 검사는 바꾸지 않습니다.

```python
def ticket_label(room):
    return f"{room['subject']} · {room['turn_count']}턴 · {room['id']}"
```

7. 로그아웃과 같은 계정 재로그인 후 문의가 수명 안에서 남는지 확인합니다. 계정 바꾸기는 미확정 질문을 삭제하며, 입력 중 초안에 대한 별도 경고를 띄우지 않습니다.

### 예상 결과

| 상황 | 예상 결과 |
| --- | --- |
| 미로그인 GET /tickets | 401 |
| A 문의 생성 | 201, 소유자는 서버가 확인한 A |
| B의 내 문의 목록 | B의 문의만 표시, A 제목 없음 |
| B가 A ID로 기존 문의 열기 | 404, A의 카드·질문·답변 미표시 |
| B가 A 문의로 상담 요청 | 404, Groq 호출과 턴 추가 없음 |
| A가 자기 ID로 다시 열기 | 200, 기존 카드와 성공 턴 복원 |
| A의 복원 후 후속 질문 | 앞선 A-확인-321과 VPN 시간 초과를 참고 |
| label 함수 수정 후 목록 | A-VPN-접속 · <성공 턴 수>턴 · <A 문의 ID> |
| 로그아웃한 토큰으로 요청 | 해당 Redis 등록이 없으므로 401 |

AI가 B에게 A의 정보를 묻도록 유도하는 문장을 답한다고 해서 권한 검사를 통과한 것은 아닙니다. 서버 응답과 실제 카드·기록 노출 여부로 판단합니다. 404는 존재 여부를 자세히 알려 주지 않기 위한 응답입니다. Groq 키 오류는 앱 로그인 오류와 구분되어 상담 요청 502로 표시되며, 곧바로 다른 사용자로 바뀌지 않습니다.
